# Terraform API identity for pve-00

The `proxmox_terraform_credentials` role runs with normal `task plan`/`task apply`. On its first apply it creates `terraform@pve`, grants the built-in `Administrator` role on `/`, creates a **privilege-separated** `provisioning` API token expiring one year after creation, grants the same role to the token, and stores the one-time token in Doppler project `home-dc-proxmox`, config `prd`, as `PROXMOX_TOKEN_ID` and `PROXMOX_TOKEN_SECRET`. The resulting token identifier is `terraform@pve!provisioning`. This is effectively **root-level Proxmox API access**: review the plan before the next full apply. Proxmox API tokens cannot access interactive system/VM consoles.

`PROXMOX_TOKEN_ID` holds the token identifier and `PROXMOX_TOKEN_SECRET` its secret. Do not paste either into Git, an Ansible variable file, a Terraform `.tfvars` file, task output, or chat. Terraform obtains its token from Doppler at runtime: `home-dc-terraform` reads its own copy of the same two names from project `home-dc-terraform`, config `prd`, so the two copies are independent (see Rotation). The legacy `proxmox-terraform-user` credential for the old cluster is not touched. This role does not write a Terraform configuration or distribute the credential to CI.

## Operator workflow

1. Create a read/write service token on `home-dc-proxmox/prd` and save it with `task doppler-token-save` ([setup](mail.md#service-token-authentication-on-macos)). **One token** serves mail reads, config checks and the Terraform secret write; it can read and change every secret in that one config, not other Doppler projects.
2. **Precondition on an already-provisioned host:** `PROXMOX_TOKEN_ID` and `PROXMOX_TOKEN_SECRET` must both exist in `home-dc-proxmox/prd` before the first run. If the host token exists but either secret is missing, the role refuses and changes nothing; it never creates or rotates a token to fill the gap. Seed the existing credential by pipe, never as an argument, for example `doppler secrets get PROXMOX_TOKEN_SECRET -p home-dc-terraform -c prd --plain | doppler secrets set PROXMOX_TOKEN_SECRET -p home-dc-proxmox -c prd` using your personal login (the service token cannot read other projects), and the same for `PROXMOX_TOKEN_ID`. To undo seeding: `doppler secrets delete PROXMOX_TOKEN_ID PROXMOX_TOKEN_SECRET -p home-dc-proxmox -c prd -y`.
3. Run `task plan`. It includes this role and never generates a token in check mode. `ansible-playbook -i inventory site.yml --check --diff --tags terraform-credentials` previews only this role. A successful plan checks read access, **not write permission**.
4. Review the full plan, then run `task apply`. On a host without the token it creates the root-equivalent Terraform identity and stores it with the same service token. If a Doppler write fails, the role lists the config again: it deletes a half-stored secret, removes the token ACL and revokes the new token only when it can confirm Doppler does not hold both secrets, and leaves everything untouched if that listing itself fails. Subsequent runs never rotate the token.
5. Confirm the token and effective permissions with `ssh pve-00 'pveum user token list terraform@pve --output-format json; pveum user token permissions terraform@pve provisioning --output-format json'`, and confirm both names exist with `doppler secrets --only-names -p home-dc-proxmox -c prd`. Do not display the values. Re-running the tagged role must be unchanged.

The role refuses to proceed unless the host token and **both** Doppler secrets all exist or all are absent, or if the stored identifier belongs to another token. It never replaces an existing token: Proxmox returns a token's secret only at creation, so automatic recreation could invalidate Terraform credentials. The Proxmox user and its ACL may remain after a failed write, but cannot authenticate without a valid token or password. A previous failed attempt left an invalid ACL for the revoked token; successful recreation makes that grant valid again.

### Rotation and access

To rotate before its one-year expiry, create a replacement token with new identifiers under a reviewed change, then update **both** copies: `home-dc-proxmox/prd` first (the record this role checks), then `home-dc-terraform/prd`. Verify Terraform access, then revoke the old token. Do not delete the stored secrets first. `Administrator` at `/` grants broad access; restrict network access to the PVE API and review/revoke this token when Terraform is retired. A Doppler service token is scoped to one config, so the saved token can also read the Gmail app password in the same config; a future dedicated config would need role and token changes.
