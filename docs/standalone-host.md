# Standalone PVE 9 host: design and operator runbook

This **optional, separately invoked** component configures an existing official-ISO Proxmox VE 9 / Debian 13 installation. It does not install Proxmox, create VMs, assign a GPU to a VM, initialise disks, change networking, join/remove clusters or remove Ceph. The repository's deployed `pve-00` workflow instead uses root `site.yml` and its focused roles; do not apply both controllers to the same host without reconciling their policies. Legacy cluster automation is retained solely for historical reference in `legacy/`; this component never imports it.

## Contract and isolation

Use `bash /absolute/repo/scripts/standalone-host.sh ACTION --inventory /absolute/inventory.yml --config /absolute/host.yml`. Inventory and config paths are mandatory and absolute. Optional `--host pve-app` confirms the unique inventory alias; without it the controller infers that alias only after validating exactly one literal host. Wrapper actions are validate, discover, plan, apply, verify, gpu-discover, gpu-plan, gpu-prepare, gpu-verify and reboot; root `task plan`/`task apply` instead run the deployed `pve-00` roles. Unknown arguments, inventory patterns, unsupported inventory variables, unknown configuration fields and multiple hosts fail closed. The controller normalises inputs into a private temporary directory, disables inventory-adjacent vars plugins, sanitises Ansible overrides, uses dedicated absolute configuration/playbook/library paths and always limits the validated alias. SSH identity comes only from the controller environment.

`validate` performs offline schema, inventory and Ansible syntax checks, even with deployment disabled. All other actions require deployment_enabled: true. Direct users must prepare an isolated Python 3.12–3.14 environment with dependencies from `standalone/requirements.txt`; the wrapper does not install dependencies or update sources. `PROXMOX_PYTHON` may select an absolute interpreter; its bin directory is also used for ansible-playbook. A missing selected interpreter fails rather than falling back. No collections are needed. Plan uses check mode and diff; apply reruns the playbook against current state, not a saved executable plan.

## Before arrival and execution

Install from the official PVE ISO using the [standalone installation guide](standalone-installation.md); review installer disk choices separately. Discover actual CPU topology, RAM, disk serials/use, NICs, storage and GPU rather than trusting a sales listing. Windows identified a Samsung NVMe with model prefix MZVKW1T0 and a 4 TB HGST HDS724040ALE640, not the listed 8 TB HDD. Confirm the NVMe's exact capacity and serial before erasure. These two drives are not a mirror. Preserve installer storage. local-lvm exists only for some installer layouts; a ZFS-root installation normally provides local-zfs instead. Edit local_expected_ids after discovery. Establish verified SSH host keys and recovery console access first. Copy inert examples into the private parent and review all values before setting deployment_enabled true. Never commit credentials.

Run validate, discover, plan, apply, verify in that order. Discovery is read-only. Plan/check mode is an approximation: it can inspect current state but cannot prove repository access, NAS access, package installation, boot refresh, backup execution or restore success. It does not run refresh commands or reboot. Apply changes timezone, explicit packages, an optionally selected repository policy, enabled NFS registrations and explicit backup schedules. Existing time sync is preserved and must be active/synchronised. No blanket package upgrades. Preserve repositories by default; no-subscription also disables a recognised dedicated unused ISO Ceph enterprise source (preserving its signing key and content), after preflight rejects configured Ceph. Mixed/unrecognised source files require manual review; changing repository policy only manages the PVE enterprise/no-subscription components in known PVE source files and refuses mixed legacy/deb822 or unrelated entries instead of rewriting them.

## Storage and backups

local_expected_ids are assertions only. Enabled NFS entries register only explicitly named exports with Proxmox; exports themselves remain NAS-owned. The component records ownership in its own host state directory. Existing entries without ownership are accepted only when exactly equivalent, without taking ownership; conflicting existing entries fail. Disabled entries are left unchanged, never deleted. Managed objects are compared before update; unrelated objects are untouched. NFS mount options never include credentials. Inspect NAS availability and free space separately.

Backup entries require explicit VM IDs, enabled target storage with backup content and a nonempty positive retention map. Runtime checks require every VM/container ID to exist. Only explicitly owned job IDs may be changed. Jobs are scheduled, never executed or pruned by this component. A missing job is created only by its explicit ID. Test application-consistent recovery and restore on a separate schedule; configuring a job does not establish a recoverable backup.

## GPU staged activation and recovery

Run gpu-discover and review every GPU/audio/other required function's full BDF, vendor/device ID, driver, framebuffer/console use and every IOMMU group peer. Enable IOMMU in firmware first. GPU preparation requires explicit BDFs and matching IDs, safe complete IOMMU groups and no duplicate IDs on unselected devices. If groups are unavailable, preparation only adds IOMMU boot parameters. Explicitly reboot, rediscover and repeat preparation; binding files are created only after isolation can be observed. After the first reboot, staged verification checks active IOMMU and isolation and reports binding pending; rediscover and prepare the binding stage after reviewing groups. gpu-verify always requires completed VFIO binding.

Set gpu.bootloader explicitly to grub or systemd-boot. Discovery checks EFI state, bootctl and proxmox-boot-tool status; file existence alone is insufficient. Preparation refuses ambiguous/mismatched boot state. CPU vendor determines the IOMMU argument. Existing kernel arguments are preserved; conflicting IOMMU, ACS override or unsafe interrupt options are rejected. Dedicated VFIO modules/config files bind selected IDs on the next boot, without runtime unbind or driver blacklists. A selected boot VGA/framebuffer requires allow_host_console_loss true and out-of-band or physical recovery access. No automatic reboot occurs.

Run gpu-plan, then gpu-prepare; review the pending reboot report. The separate reboot action is the only action that reboots, waits for reconnection, and runs baseline verification plus GPU verification when enabled. gpu-verify checks the active command line, isolation groups and vfio-pci binding after reboot. Baseline verify intentionally does not require pending GPU changes to be active.

Recovery: boot a known-good kernel from the physical console and temporarily remove intel_iommu=on/amd_iommu=on, iommu=pt and vfio-pci.ids from its boot entry if required. Remove `/etc/modules-load.d/standalone-vfio.conf`, `/etc/modprobe.d/standalone-vfio.conf` and `/etc/initramfs-tools/hooks/standalone-vfio`; remove only the added IOMMU tokens from `/etc/default/grub.d/90-standalone-iommu.cfg` (or remove that dedicated file), or restore `/etc/kernel/cmdline` from the backup path reported during preparation. Run update-initramfs -u -k all and the reviewed update-grub or proxmox-boot-tool refresh, then explicitly reboot. Keep the pre-change backup until recovery has been tested. Do not remove unrelated boot arguments or driver settings.

## Legacy and validation boundary

Root `site.yml` and `Taskfile.yml` are the active, already-deployed `pve-00` role workflow. This alternative component is isolated behind `scripts/standalone-host.sh` and its own `standalone/ansible.cfg`; it is **not** imported by the root playbook. The archived `legacy/site-cluster.yml` is historical and unsupported for this host. Do not mix these controllers or reconstruct cluster automation without separate review.

Offline tests exercise schema rejection, inventory isolation, wrapper argv/SSH environment, first-run check-mode helper behaviour, GPU token/bootloader/isolation checks and storage/job comparison. Syntax checks are offline. Hardware execution, repeat-apply idempotence, NAS availability, scheduled backup execution and restore, and boot/recovery validation require a separately authorised lab run.

Apply validates all requested settings in a read-only preview pass before its first write. External races and command failures can still leave a partial apply; this is not an API transaction. Disabled and absent NFS/backup entries are unmanaged, never requests to remove storage or disable schedules.

Controller support follows the [official Ansible release matrix](https://docs.ansible.com/projects/ansible/latest/reference_appendices/release_and_maintenance.html): this implementation pins ansible-core 2.21.5 and supports controller Python 3.12–3.14. Target Python is provided by the PVE 9 / Debian 13 installation.
